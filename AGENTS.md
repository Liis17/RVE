# RVE

Игровой движок на Rust с рабочим оконным путём на winit и Vulkan renderer на ash. Основная карта проекта находится в `Obsidian/RVEVault/Index.md`.

- Храни назначения компонентов, публичные контракты, зависимости, ключевые потоки, ограничения и подтверждённые причины действующих решений. Указывай реальные пути исходников и важные символы.

- Перед созданием заметки найди существующую по назначению и исходникам. Новую значимую заметку добавь в навигацию `Index.md`.
- Удалённые методы и неверные сведения убирай из описаний. При переименовании заметок исправляй wikilinks, обычные Markdown-ссылки, пути в `AGENTS.md` и сохранённые пути Obsidian.

## Быстрые команды

Запускай из корня workspace:

~~~powershell
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo build --workspace
cargo test --workspace
cargo run -p sandbox
cargo run -p sandbox -- --frames 120
cargo run -p sandbox -- --frames 120 --render-scale 0.5
cargo run -p sandbox -- --frames 300 --resize-test
~~~

Для CLI и границ текущего Vulkan пути смотри `README.md`; для контрактов — соответствующие заметки в `Obsidian/RVEVault/`.

## Правила работы с Git репозиторием

- Запрещено создавать ветки для работы со своей задачей, всегда работать с текущей веткой, если явно не сказано работать в отдельной

- Если большая задача с планом, после каждого завершённого этапа делай коммит со своими изменениями. Пуш не делай, если явно не сказано.

- Сообщение коммита должно кратко и понятно описывать результат. Весь текст сообщения — не более 200 символов, включая пробелы и переносы строк.

- Если описание не помещается в 200 символов, сначала сократи формулировку. Если изменения решают несколько самостоятельных задач, раздели их на несколько логически завершённых коммитов с отдельными короткими сообщениями. Каждый коммит должен содержать целостное изменение.

## Поведенческие правила

Правила для снижения типичных ошибок при написании кода.

**Компромисс:** эти правила смещают баланс в сторону осторожности, а не скорости. Для тривиальных задач — действуй по ситуации.

### 1. Думай перед кодом

**Не предполагай. Не скрывай сомнения. Показывай компромиссы.**

Перед реализацией:

- Явно формулируй свои допущения. Если не уверен — спроси.
- Если возможны несколько трактовок — покажи их, не выбирай молча.
- Если есть более простой подход — скажи об этом. Возражай, когда это оправдано.
- Если что-то неясно — остановись. Назови, что именно сбивает с толку. Спроси.

### 2. Простота прежде всего

**Минимум кода, решающего задачу. Ничего спекулятивного.**

- Никаких функций сверх запрошенного.
- Никаких абстракций для одноразового кода.
- Никакой «гибкости» или «настраиваемости», которую не просили.
- Никакой обработки ошибок для невозможных сценариев.
- Если написал 200 строк, а можно 50 — перепиши.

Спроси себя: «Сказал бы senior-инженер, что это переусложнено?» Если да — упрости.

### 3. Хирургические правки

**Трогай только то, что необходимо. Убирай только свой беспорядок.**

При редактировании существующего кода:

- Не «улучшай» соседний код, комментарии или форматирование.
- Не рефактори то, что не сломано.
- Соблюдай существующий стиль, даже если сделал бы иначе.
- Если заметил несвязанный мёртвый код — упомяни, но не удаляй.

Когда твои изменения создают «сирот»:

- Удаляй импорты/переменные/функции, которые стали неиспользуемыми ИЗ-ЗА твоих изменений.
- Не удаляй ранее существовавший мёртвый код без запроса.

Тест: каждая изменённая строка должна напрямую следовать из запроса пользователя.

### 4. Выполнение, ориентированное на цель

**Определи критерии успеха. Повторяй до проверки.**

Превращай задачи в проверяемые цели:

- «Добавь валидацию» → «Напиши тесты на невалидный ввод, затем сделай, чтобы они проходили»
- «Исправь баг» → «Напиши тест, воспроизводящий баг, затем сделай, чтобы он проходил»
- «Отрефактори X» → «Убедись, что тесты проходят до и после»

Для многошаговых задач кратко изложи план:

```
1. [Шаг] → проверка: [контроль]
2. [Шаг] → проверка: [контроль]
3. [Шаг] → проверка: [контроль]
```

Сильные критерии успеха позволяют работать автономно. Слабые («просто заставь работать») требуют постоянных уточнений.

**Эти правила работают, если:** в диффах меньше лишних изменений, меньше переписываний из-за переусложнения, а уточняющие вопросы возникают до реализации, а не после ошибок.

### Актуальность документации сторонних API

Перед написанием кода, использующего стороннюю библиотеку или фреймворк, обязательно обращайся к Context7 (`use context7`) за актуальной документацией и примерами. Это правило действует для любых библиотек, включая Android SDK, Jetpack, WPF, .NET и NuGet.

## Сначала определить исходный режим сессии

Правила оркестрации зависят от того, **в каком режиме сессия началась**,
а не только от её текущего режима.

- **Сессия началась в Plan Mode:** обязательна описанная ниже цепочка
  самостоятельного планирования, уточнений, независимого ревью плана,
  подтверждения пользователем, делегированной реализации, ревью кода
  и сборки с тестами. Основной агент код не пишет.
- **Сессия началась без Plan Mode:** выполняй поставленную пользователем
  задачу обычным способом. Консультация наставника и делегирование кода
  или проверок доступны по необходимости, как описано в этом разделе.

Определи исходный режим по сведениям о запуске или истории текущей сессии
и сохраняй его в контексте работы, включая передачу контекста после сжатия.
`interactionMode` из текущего ответа T3 показывает текущий режим;
после переключения он не доказывает, каким был режим при запуске.
Если исходный режим установить нельзя и это влияет на выбор процесса,
уточни его у пользователя, не выбирая ветку по догадке.

Само переключение режима, появление краткого плана в ответе или создание
плана субагентом не меняет исходный режим сессии. Изменить согласованный
порядок работы можно по явному указанию пользователя.

## Работа в сессии, начатой без Plan Mode

Основной агент изучает задачу и нужный код, выполняет запрос пользователя
и проверяет результат. Он может самостоятельно писать и исправлять код.
При неоднозначностях, требующих решения пользователя, задавай вопросы.
Обязательное утверждение плана, ревью плана и цепочка с Sonnet из правил
Plan Mode к этой ветке не применяются.

### Консультация наставника при проблемах

Если возникла проблема и нужен дополнительный взгляд, можно создать
субагента-наставника **Sol 6.1 (`gpt-6.1-sol`) на `high`** или
**Opus 5.5 (`claude-opus-5-5`) на `high`**. Выбери одного из них
с учётом доступности и указаний пользователя. Консультация необязательна.

Передай вопрос, контекст задачи, относящийся к проблеме код, наблюдаемые
ошибки и уже проверенные гипотезы. Попроси объяснение и рекомендации;
наставник не изменяет файлы. Основной агент оценивает ответ и решает,
как продолжать работу. Новый пользовательский выбор уточняй у пользователя.

### Делегирование кода и тестов после изучения задачи

Если тема изучена достаточно, чтобы передать конкретное задание,
можно поручить написание кода и запуск сборки или тестов субагентам
**Luna 6 или новее на `max`**. Выбирай новейшую доступную модель
семейства Luna версии не ниже 6, поддерживающую `max`; базовая модель —
`gpt-6-luna`. Полный утверждённый план для такого делегирования не требуется.

Передай цель, нужные исходники, границы изменений, ограничения и критерии
готовности. Для проверки передай также необходимые команды и область
изменений. Попроси отчёт о выполненной работе; при сбоях — что и где
сломалось, результаты команд и существенные сообщения об ошибках.
Основной агент проверяет отчёты и доводит исходную задачу до завершения.
Не считай пропущенные или недоступные проверки успешными.

Перед созданием любого субагента проверь актуальные модели, провайдеры
и уровни рассуждения через T3 `orchestrator_capabilities` и передавай
выбранный уровень явно. В Codex это настройка `reasoningEffort`,
у Claude — `effort`; сверь их с каталогом. Недоступную модель или уровень
не подменяй молча, если решил делегировать работу: согласуй замену.

Используй нативный инструмент для того же провайдера, если он поддерживает
модель и уровень; для другого провайдера или неподдерживаемой модели —
T3 `delegate_task`. Сохраняй идентификаторы задач и не дублируй активную
работу. Создавай дочерние задачи, а не отдельные основные беседы.

## Оркестрация в Plan Mode

Эти правила применяются только к сессиям T3 Code, изначально начатым
в Plan Mode. До подтверждения финального плана пользователем не начинай
реализацию. Переход в режим реализации после подтверждения плана
не отменяет выбранную для этой сессии цепочку оркестрации.

### Самостоятельная подготовка

Основной агент сам изучает поставленную задачу, инструкции проекта,
соответствующий код и существующие проверки. Не делегируй изучение задачи,
чтение кода, интервью с пользователем или написание первоначального плана
субагентам.

Выяви развилки, неоднозначности, недостающие требования и зависимости
до начала реализации. Факты, которые можно выяснить по коду или среде,
проверь самостоятельно. Решения, требующие выбора пользователя, обсуждай
с ним, предлагая рекомендуемый вариант и объясняя последствия.
Дожидайся ответа на существенные вопросы; не подменяй его предположением.

Если установлен `grill-me` или доступен аналогичный навык для уточнения
требований, прочитай его инструкции и используй при интервью. Если это
навык-обёртка, прочитай также навык, на который он ссылается. Если подходящего
навыка нет, проведи уточнение самостоятельно; установка навыка не требуется.
При использовании такого интервью задавай вопросы по одному и разрешай
зависимые решения последовательно.

Составь план реализации на основе изученного кода и ответов пользователя.
Укажи цель, границы работы, принятые решения, затрагиваемые компоненты,
последовательность изменений и способ проверки результата.
Перед независимым ревью убедись, что нет открытых вопросов к пользователю
и неразрешённых неоднозначностей, обнаруженных на этом этапе.

### Независимое ревью готового плана

Только после подготовки плана и завершения уточнений создай субагента
для независимого ревью. Модель — Sol 6.1 (`gpt-6.1-sol`):

- `high` — обычная задача.
- `xhigh` (Extra High) — большая и сложная задача: например, несколько
  взаимосвязанных подсистем, изменение контрактов или сложная миграция.

Получи актуальный каталог через T3 `orchestrator_capabilities` и проверь
модель, провайдер, возможность запуска субагента и доступные настройки
рассуждения. Передай выбранный уровень явно, а не полагайся на значение
по умолчанию. В каталоге Codex это настройка `reasoningEffort`.
Если нужная модель или уровень недоступны, сообщи пользователю и согласуй
замену; не пропускай ревью и не подменяй модель молча.

Используй инструменты создания субагентов, а не отдельной основной беседы.
Для того же провайдера предпочитай нативный инструмент, если он поддерживает
выбранную модель и уровень рассуждения. Иначе используй T3 `delegate_task`
с выбранными `providerInstanceId`, `model` и настройками рассуждения.

Передай ревьюеру полный план, исходную задачу, согласованные требования,
решения пользователя, ограничения и необходимые пути к исходникам.
Не рассчитывай на автоматическое наследование истории беседы.
Задача ревьюера — проверить полноту, выполнимость, соответствие коду,
пропущенные развилки, риски и достаточность проверок. Ревьюер может читать
код, но не изменяет файлы, не начинает реализацию и не запускает своих
субагентов.

Попроси вердикт о готовности плана и конкретные замечания с обоснованием:
что исправить и какие решения требуют ответа пользователя. Дождись
завершения ревью перед выдачей финального плана.

Для T3-делегирования сохраняй `taskId`; проверяй состояние существующей
задачи, прежде чем запускать замену. При необходимости нового раунда ревью
создай новую задачу через `delegate_task`, передав исходный запрос,
обновлённый план, предыдущие замечания, ответы и оставшиеся возражения.
У каждого раунда отдельный `clientRequestId`, стабильный при повторах
его запуска. Не продолжай ревью через `t3_thread_send` на `childThreadId`.

### Разрешение замечаний и финальный план

Основной агент оценивает замечания по коду, требованиям и принятым решениям.
Простые поправки к плану, не создающие нового выбора и не меняющие
согласованные требования, внеси самостоятельно. Отклонённые замечания
обоснуй; вердикт ревьюера сам по себе не заменяет проверку.

Если ревью выявило новую развилку, неоднозначность или проблему, решение
которой требует выбора пользователя, задай уточняющий вопрос и дождись
ответа. Не выбирай за пользователя только ради завершения плана.

После разрешения замечаний и новых вопросов обнови план и выдай его
пользователю на подтверждение. Финальный план должен включать принятые
решения и проверки, без открытых вопросов, блокирующих реализацию.
Подтверждение плана не заменяется положительным вердиктом субагента.

## Оркестрация реализации

Эти правила применяются только к сессиям T3 Code, изначально начатым
в Plan Mode, при реализации подтверждённого пользователем плана.
Они продолжают действовать после переключения из планирования в реализацию.
Основной агент отвечает за план и координацию: распределяет
работу, контролирует выполнение, оценивает отчёты и сообщает результат.
Он сам не пишет и не исправляет код, включая тесты. Изменения кода,
интеграцию изменений и разрешение конфликтов поручай субагентам.
Для сессий, начатых без Plan Mode, действуют отдельные правила обычной работы;
эта обязательная цепочка и запрет основному агенту писать код к ним не относятся.

### Выбор моделей

Перед делегированием получи актуальный каталог T3 через
`orchestrator_capabilities`. Проверь возможность запуска субагентов
у выбранных провайдеров и поддержку требуемых уровней рассуждения.

- Реализация, сборка, тесты и простые исправления: **Luna 6 или новее**
  с рассуждением **`max`**. Выбирай новейшую доступную модель семейства Luna
  версии не ниже 6, поддерживающую `max`. Базовый идентификатор — `gpt-6-luna`.
  Сравнивай версии численно, а не по порядку в каталоге или строковой сортировке.
  Не считай другую модель новой Luna только из-за похожего названия.
- Ревью кода: **Sonnet 5.5**, `claude-sonnet-5-5`, рассуждение **`high`**.
- Сложные исправления: **Sol 6.1**, `gpt-6.1-sol`, рассуждение **`medium`**.

Передавай уровень рассуждения явно. В каталоге Codex настройка называется
`reasoningEffort`, у Claude — `effort`; сверяй имена и значения с каталогом.
Точные идентификаторы провайдеров также бери из каталога текущей среды.
Если модель, уровень или возможность запуска отсутствуют, сообщи пользователю
и согласуй замену. Не заменяй исполнителя собой и не снижай уровень молча.

### 1. Делегировать написание кода

Создай субагента Luna 6+ на `max` и передай подтверждённый план,
исходную задачу, решения пользователя, инструкции проекта, границы изменений,
нужные пути и критерии готовности. Не рассчитывай на автоматическую передачу
истории беседы. Попроси отчёт об изменённых файлах, реализованных пунктах
плана, отклонениях и оставшихся проблемах.

Если в плане есть независимые части, например в двух или трёх отдельных
проектах, можно запустить несколько субагентов Luna 6+ на `max` параллельно.
Перед запуском проверь отсутствие пересечений по файлам, общим контрактам
и зависимостям. Назначь каждому свою область изменений; при необходимости
используй изолированные рабочие копии. Зависимые или пересекающиеся части
выполняй последовательно.

Основной агент отслеживает выполнение и разрешает организационные вопросы.
Если возник новый выбор, меняющий подтверждённый план или требования,
обсуди его с пользователем до выполнения соответствующей части.

### 2. Передать завершённый код на ревью

Дождись завершения единственного исполнителя или всех параллельных
исполнителей. Если изменения находятся в разных рабочих копиях, поручай
их интеграцию субагенту Luna 6+ на `max` до итогового ревью.

Создай субагента **Sonnet 5.5 на `high`** для изучения и ревью написанного
кода. Передай план, требования, границы итоговых изменений, отчёты
исполнителей и пути к исходникам. Для нескольких проектов включи все
затронутые проекты и их взаимодействия в область ревью.

Ревьюер проверяет соответствие плану, ошибки поведения, пропущенные случаи,
проблемы взаимодействия компонентов и регрессии. Он не исправляет код.
Попроси вердикт и отчёт по каждой проблеме: серьёзность, файл и место,
объяснение ошибки, условия воспроизведения и рекомендуемое исправление.
Не требуй находить проблемы, если обоснованных замечаний нет.

### 3. Запустить сборку и тесты

После получения ревью создай отдельного субагента **Luna 6+ на `max`**
для запуска сборки и подходящих тестов итогового кода. Передай инструкции
проекта, область изменений, требуемые проверки из плана и замечания ревью.
Проверки нужны и при наличии замечаний: их отчёт дополняет ревью.

Субагент использует предусмотренные проектом команды и не исправляет
исходники, не отключает проверки и не ослабляет тесты ради успешного результата.
Попроси отчёт с командами, результатами, кодами завершения, выполненными
и пропущенными проверками. При сбоях он сообщает, что и где сломалось,
с существенными фрагментами ошибок и местами в коде, если они определены.
Предположение о причине должно быть отделено от установленного факта.

Если сборка блокирует запуск тестов или среда не позволяет выполнить
проверку, это указывается в отчёте. Пропущенные проверки не считаются успешными.

### 4. Исправить проблемы новым субагентом

Если ревью выявило проблемы или сборка и тесты завершились с ошибками,
основной агент собирает замечания в конкретное задание и создаёт нового
субагента для исправления:

- **Luna 6+ на `max`** — локальная и понятная проблема с ограниченным
  исправлением в рамках согласованного плана.
- **Sol 6.1 на `medium`** — сложная проблема: неясная причина, несколько
  взаимодействующих компонентов, необходимость пересмотреть технический подход.

Оценивай сложность по содержанию проблемы, а не только по количеству ошибок.
Передай новому исполнителю исходный план, текущие изменения, отчёты ревью
и проверок, условия воспроизведения, ограничения, конкретные указания
и критерии исправления. Новый исполнитель не должен восстанавливать контекст
по догадкам. Основной агент сам исправления не вносит.

Если исправление требует нового продуктового выбора или изменения
согласованных требований, сначала получи решение пользователя.
После исправления повтори ревью у Sonnet 5.5 `high`, затем сборку и тесты
у Luna 6+ `max` для обновлённого кода. Успех прежних проверок не подтверждает
корректность последующих изменений. Не запускай без изменений одинаковые
попытки исправления: учитывай новые результаты и уточняй задание.

### Управление субагентами и завершение

Используй инструменты делегирования дочерних задач. Для того же провайдера
предпочитай нативный инструмент, если он поддерживает требуемую модель
и уровень рассуждения. Для другого провайдера или неподдерживаемой нативным
инструментом модели используй T3 `delegate_task`. Отдельные основные беседы
через `t3_thread_launch` или `create_threads` не заменяют субагентов.
Исполнители не делегируют работу дальше без указания основного агента.

Сохраняй идентификаторы задач и проверяй состояние перед повторным запуском,
чтобы не дублировать активную работу. Для каждого T3-раунда ревью создавай
новую задачу через `delegate_task`, передавая исходный запрос, обновлённые
изменения, предыдущие замечания, ответы на них и нерешённые возражения.
Каждый раунд имеет отдельный `clientRequestId`, стабильный при повторе
его запуска. Не продолжай ревью через `t3_thread_send` на `childThreadId`.

Сообщай пользователю, что работа завершена и проверки прошли, только после
выполнения плана, разрешения замечаний ревью и успешного завершения
требуемой сборки и тестов итогового кода. Кратко укажи, что сделано
и какие проверки выполнены. Если остались проблемы или проверки недоступны,
сообщи их явно вместо утверждения, что всё в порядке.

### Точные идентификаторы провайдеров и моделей T3

Перед каждой делегацией сверяй актуальный каталог и уровни рассуждения. Используй следующие подтверждённые идентификаторы и настройки:

- Реализация, проверки и простые исправления: provider `codex`, model `gpt-6-luna`, `reasoningEffort: max`.
- Независимое ревью плана: provider `codex`, model `gpt-6.1-sol`; `reasoningEffort: high` для обычных задач и `xhigh` для больших и сложных задач.
- Ревью кода: provider `claudeAgent`, model `claude-sonnet-5-5`, `effort: high`.
- Сложные исправления: provider `codex`, model `gpt-6.1-sol`, `reasoningEffort: medium`.
- Необязательная консультация в сессии без Plan Mode: provider `codex`, model `gpt-6.1-sol`, `reasoningEffort: high`, либо provider `claudeAgent`, model `claude-opus-5-5`, `effort: high`.

Передавай параметры явно. Если нужный provider, model или уровень недоступен, согласуй замену с пользователем; не выбирай её молча.
